# 版本发布、Docker 更新与验证

正式版本采用 `主版本.次版本.修订号`，候选版本在末尾加 `-rc.N`，其中 N 从 1 开始递增。当前文档以正式版 `1.1.3` 为准，对应标签 `v1.1.3` 和镜像标签 `1.1.3`。应用在已认证的 `/api/state` 和健康接口 `/api/health` 返回 `version`，用于核对实际运行版本；直接请求受保护的健康接口返回 401，不等于容器不健康。

## 从 v1.1.2 升级到 v1.1.3

本版修复录音保存错误路径，统一上传、存储与备份的 AMR-NB 文件头、2 MiB 上限和文件名校验；录音文件及目录同步完成后再提交数据库索引。同时优化推送成功统计与录音角标检查，修正录音恢复提示，并整理使用、部署、备份和安全文档。完整变更见[更新记录](../CHANGELOG.md#113)。

**沿用 schema 21、现有配置及两种备份格式，不新增迁移。** 确认 `v1.1.3` 标签的镜像工作流成功后，沿用完整 Compose 文件、原数据卷和数据目录，将镜像改为 `ghcr.io/battery233/sim-harbor:1.1.3` 后按[切换流程](#3-核对配置并切换)重建服务。现有升级脚本可继续使用，只需传入新版本；无需手工 SQL、恢复数据库或重设板子、上传地址、令牌与 Tunnel。

新上传会拒绝不受支持的 AMR-WB、损坏或不完整的文件头；这属于格式入口校验，不是完整音频解码验证。历史录音不自动转换、删除或修复；若旧文件不符合含录音备份的校验规则，仍会明确报错，保留原文件供核对。从 v1.1.1 或更早版本升级时，继续核对下方相应版本的 schema 与备份兼容性边界。

## 从 v1.1.1 升级到 v1.1.2

本版增加可选录音 ZIP、跨浏览器播放状态、角标及系统推送查询。schema 20 首次启动自动迁到 **21**，保存录音首次播放时间、容量提醒历史和异常任务记录时间，原配置直接沿用；旧浏览器本地播放标记不导入，历史录音按未播放开始计数。v1.1.1 及更早版本不能直接打开新库，回退需使用升级前数据库，不能手改版本号。备份不勾选录音仍为格式 1，勾选后为格式 2；格式 2 或 schema 21 必须由兼容的新工具恢复。恢复到新目录且保持外发保护。

确认 `v1.1.2` 标签的镜像工作流成功后，沿用完整 Compose 文件和原数据卷，仅把镜像版本改为 `ghcr.io/battery233/sim-harbor:1.1.2` 后重建服务。首次启动自动迁移，无需手工 SQL、恢复数据库或重新设置板子。沿用下方[切换流程](#3-核对配置并切换)，已有自用升级脚本也应保留相同项目、全部覆盖文件及数据卷；不能通过重新拉取 `1.1.1` 获得这些功能，也不要移动已发布标签。

从 `1.1.2-rc.1` 升级到正式版沿用 schema 21，不新增数据库迁移；仅收紧备份区勾选项与按钮间距并定版。

“推送记录”默认全部类型，首页统计也包含系统提醒。旧异常任务沿用已有历史；旧容量提醒只有私有进度，从本版开始记录可查询任务，不补建已发送历史。容量提醒阈值、退避与恢复保护保持有效。进度文件会增加关联任务的可选字段；回退旧版需同时使用升级前数据库和兼容的 `voicemail-capacity.private.json` 副本，不能只换旧镜像或清空进度。升级后核对版本、容器健康、历史、配置、录音播放与角标；普通升级无需为验收主动拨号、发短信或在生产恢复备份。

## v1.1.1 的数据库兼容性

录音缺失与迟到通知使用 schema 20；v1.1.0 至 rc.4 首次升级时自动迁移，rc.5 升级不增加迁移，保留既有通知编号与结果，不为历史来电补建等待任务。旧配置可直接读取，无需重设板子。备份 ZIP 格式仍为 1，包含通知阶段与等待状态，不包含录音文件。旧版 v1.1.0 至 v1.1.1-rc.4 不能直接打开 schema 20；回退需使用升级前数据库和兼容配置，不能只换回旧镜像。恢复旧备份后，新程序仍会迁移并进入恢复保护。

## 标签、Release 与镜像的关系

| 项目 | 作用 | 创建方式 |
| --- | --- | --- |
| 应用版本 `1.1.3` | 网页和 API 显示的运行版本 | 在源码与构建配置中维护 |
| Git 标签 `v1.1.3` | 固定本版源码对应的提交 | 本地创建后推送，或在 GitHub 发布页面创建 |
| GitHub Release | 展示版本说明、源码包及附件 | 在 Releases 页面基于标签发布 |
| GHCR 镜像 `:1.1.3` | Docker 安装与更新使用的构建产物 | `Release image` 工作流构建并上传 |

当前 [Release image 工作流](../.github/workflows/release.yml)仅在收到 `v*` 标签推送后运行，负责镜像验证与发布；Release 页面由维护者另外填写和发布。本地提交、普通 `main` 分支推送均不触发镜像上传，当前也没有手动触发或定时发布入口。

标签去掉 `v` 后必须是三段数字，可带 `-rc.N` 后缀，并与后端版本、`web/package.json` 完全一致，否则工作流停止。构建验证通过后，工作流使用 `GITHUB_TOKEN` 的 `packages: write` 权限上传 `ghcr.io/<仓库所有者>/<仓库名>:<版本>`，同时提供 `linux/amd64` 和 `linux/arm64`；不会生成 `latest` 标签或执行实例部署。包可见性及外部拉取权限需在 GitHub Packages 中单独核对。

## 发布顺序

1. 整理代码、文档、版本号与更新记录，运行 CONTRIBUTING 中与改动相关的检查。
2. 核对版本号一致：`internal/version/version.go`、`web/package.json`/锁文件、Dockerfile 标签、Compose 默认镜像与本版文档。
3. 按部署目标分别构建和验证架构镜像。使用合成数据检查启动、健康、备份/恢复和迁移确认。
4. 确定包含本版最终代码与文档的提交，核对工作区和提交：

   ```sh
   git status --short --branch
   git log -1 --oneline
   ```

   使用 GitHub Desktop 时，先推送 `main`，再在 History 中选中定版提交，通过 Create Tag 创建 `v1.1.3` 并推送标签。不要假定在命令行创建的标签会随 Desktop 推送分支一并上传。已有同名标签时先核对指向；发布标签必须对应最终定版提交。已发布版本保持固定，后续修正使用新提交及相应版本。
5. 打开 Actions → Release image，等待验证与发布成功，并核对镜像的 amd64/arm64 架构清单。工作流成功后再检查 Packages 中对应镜像版本。
6. 在 GitHub 的 Releases → Create a new release 中选择已有标签，填写标题和本版说明。RC 版本标记为预发布，不设为最新正式版，再 Publish release。也可在该页面创建新标签并选择目标提交，再发布以触发构建，步骤见 [GitHub 官方指南](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)。
7. 分享镜像时核对 GHCR 包的可见性；公开使用测试匿名拉取，私有分享准备相应读取权限。复用与分发按 README 的许可说明处理。

GitHub Release、镜像发布与云端部署各有独立结果，按上述顺序核对后，再安排实例更新。

## 本机构建与镜像发布

已发布标签时，可在目标服务器从该版本源码构建。先确认工作区修改已保存，再选择版本：

```sh
git fetch origin --tags
git checkout --detach v1.1.3
docker build --platform linux/amd64 -t sim-harbor:1.1.3 .
docker image inspect sim-harbor:1.1.3 --format '{{.Os}}/{{.Architecture}}'
```

尚未发布标签时，也可从已经核对的远端提交构建；记录实际提交 SHA，便于后续对应源码与镜像。

准备新镜像期间保留现有运行配置与旧镜像。应用镜像、业务数据和私有配置分别管理，更新时更容易验证和回退。

使用已成功发布的包时：

```sh
docker pull ghcr.io/battery233/sim-harbor:1.1.3
docker buildx imagetools inspect ghcr.io/battery233/sim-harbor:1.1.3
```

确认包含目标架构。生产环境可进一步固定镜像清单摘要，使升级和回退目标可追溯。私有包使用具备 `read:packages` 权限的凭据在主机私密登录。

## 已有实例升级

下面沿用[Docker 安装](deployment-docker.md)中的项目名 `sim` 与 `deploy/site.private.yaml`。既有实例按实际参数操作，保留原项目名、全部覆盖文件、端口、数据卷和数据目录。已有 `deploy/release.private.yaml` 时，该文件始终放在最后。

以下逐版小节是历史兼容性说明，其中镜像、页面名称和 ZIP 能力属于对应版本。升级当前版本先看[从 v1.1.2 升级到 v1.1.3](#从-v112-升级到-v113)，较早版本还需核对途经的迁移边界；不需要逐个部署中间版本。下方通用操作示例统一使用 `1.1.3`，逐条执行，任何一步失败后停止并保留现场。

### 从 v1.1.0 或候选版升级到 v1.1.1

本版保留 rc.4 的可选 HTTPS 公网录音接收、代理来源保护、限流和容量提醒；增加接通结束后 3 分钟未收到录音的提醒、迟到录音的独立通知、短信与通话混合推送记录、录音逐条删除和播放标记，以及可保存到服务器的后台数据库备份。具体行为见[留言说明](voicemail.md)和[数据维护](data-maintenance.md)。

从 v1.1.0 至 rc.4 升级，首次启动会在事务中将 schema 19 自动升级至 20，即使留言关闭也会迁移。rc.5 已使用 schema 20，升级本正式版不再新增迁移。保留既有通知编号、发送结果及恢复保护，不为历史来电补建录音等待任务。旧配置可原样读取；已有开关、地址、令牌、卡槽及设备白名单保留，无需重设板子、Tunnel、端口或数据卷。新备份容量字段可缺省，不需要补填。

沿用原配置、完整 Compose 文件及数据卷，仅把版本覆盖文件的镜像改为 `ghcr.io/battery233/sim-harbor:1.1.1` 后重建服务；无需手工执行 SQL、`restore` 或重新完成迁移确认。镜像需在对应标签的工作流成功后核对使用。失败后停止并保留现场，不自动回退。

**v1.1.0 至 rc.4 不能直接打开升级后的 schema 20。** 回退必须使用升级前兼容的数据库，并核对[公网配置字段](#公网录音配置的兼容性)。如果保存了非零 `backup_max_storage_mib`，旧程序不认识该字段，也需从旧版配置副本中移除。备份 ZIP 格式仍为 1，数据库上限为 512 MiB、ZIP 为 544 MiB；超过旧版上限的备份需用新版维护工具检查和恢复。ZIP 不含 AMR，需另行保存录音目录。

公网接收仍需操作者主动配置 HTTPS 上传域名及代理来源；升级不会自动开启录音、修改 Tunnel 或发送设置短信。具体固件的 TLS 兼容性、上传稳定性及本版新增提醒需要在目标环境核对，离线测试不能替代现场验证。

正式镜像使用 `1.1.1` 固定标签，不覆盖既有版本，也不生成 `latest`。升级后核对网页版本为 `1.1.1`、容器健康、历史与配置、双卡状态、现有录音可播放/下载，以及“短信与通话推送”中的旧记录；原有上传地址和来源配置应保持一致。新后台备份只在主动生成后占用数据卷空间。普通升级验收不需要主动拨号或发送短信。

### 从 v1.0.4 升级到 v1.1.0

v1.1.0 增加默认关闭的[留言](voicemail.md)，包括接通提示音、本地 AMR 上传、网页播放与下载、留言通知以及经过确认的板子启用和恢复操作。新增能力的合成测试不代替 v153 或其他固件的真机完整链路验收。

既有配置缺少留言字段时默认关闭，无需为了升级补填卡槽、提示音或上传地址。云端继续使用原有短信、来电和通知功能，保持留言关闭；本版不支持云端录音上传，也不要求为升级调整端口、Tunnel 或板子参数。云端录音和包含录音的备份见[开发规划](roadmap.md)。

首次打开原数据库时，应用在事务中自动从 schema 17 升至 19：schema 18 增加留言索引与通知类型，schema 19 增加不含密码或指令正文的控制短信账本。留言关闭也会迁移。沿用原项目名、完整 Compose 文件、配置和数据卷，仅更新版本覆盖文件里的镜像引用并重建服务即可；不执行 `restore`、不手工改库，也不需要重新完成已有的迁移确认。历史短信、分片上报关联、来电、通知状态、卡偏好与恢复保护保留。

升级前用 v1.0.4 保存 schema 17 数据库 ZIP 和私有配置，保留旧镜像供回退。新库不能直接交给 v1.0.4 或更早版本；回退需保留升级后的最新数据，再使用升级前兼容备份恢复到独立目录，不要修改 `schema_version` 降级。若已有录音，另行保存 `voicemail/`：ZIP 含索引和控制账本，不含 AMR，恢复录音需把单独保存的目录放回数据目录。

先拉取并核对已成功发布的 `1.1.0` 镜像，再更新 `deploy/release.private.yaml` 并按下方步骤重建。只拉取镜像不会替换运行容器。存在版本覆盖文件的实例，所有 Compose 操作都继续携带同一组文件，且版本覆盖文件放在最后。升级后核对版本为 `1.1.0`、容器健康、原历史和配置、板子重连及双卡状态；等待自然短信观察入库与通知，无需自动发送短信、拨号或开启留言。失败后停止操作并保留现场，不自动回退。

### 从 v1.0.3 升级到 v1.0.4

v1.0.4 增加[允许分片时间差的组装](protocol-notes.md#允许分片时间差的组装)，数据库从 schema 16 升至 17，以保存各次分片上报与组装记录的关联。沿用原数据卷和配置、更换应用镜像后，新版首次启动会自动完成迁移，无需手工执行 SQL、导入数据库或重新完成迁移确认。

首次运行 v1.0.4 时事务创建关联表，不批量合并、补发或改写历史短信。原数据卷、现有配置与迁移确认继续沿用；有足够分组信息的旧未完成短信，可在收到后续真实分片时完成并按原规则通知。缺少组信息的历史记录保持原状。

升级前保存 schema 16 数据库 ZIP 和私有配置，并保留旧镜像。升级后的 schema 17 不能直接交给 v1.0.2/v1.0.3；回退需保留最新数据后，使用兼容旧版的升级前备份恢复到独立目录，按[数据维护](data-maintenance.md)核对新增业务和恢复外发保护。不要手工修改版本字段或删除关联表来降级。

### 从 v1.0.2 升级到 v1.0.3

本版增加[自定义管理鉴权请求头](configuration.md#自定义鉴权请求头)，继续使用数据库 schema 16，不迁移原库。升级前保存数据库 ZIP 和私有配置，按下方步骤切换镜像，沿用原项目名、全部 Compose 文件、数据卷及数据目录；无需执行 `restore` 或重新完成迁移确认。

未设置 `admin_token_header` 的现有实例继续使用 `Authorization: Bearer <管理token>`。需要与反向代理 Basic Auth 共存时，先升级应用，再在“系统配置 → 管理访问”填写例如 `X-SIMHarbor-Authorization`，保存后确认重启应用，并刷新网页。Token 不变，代理需透传该头；普通 API、下载和健康检查同步使用当前生效配置。

升级后核对网页版本、容器健康、原历史与配置。可使用合成环境或自己的测试实例验证 Basic Auth 与自定义头共存；普通维护无需发送短信、拨号或重放历史。

**回退至 v1.0.2 前先检查配置兼容性。** 旧版不认识 `admin_token_header`：如果启用过自定义头，先在 v1.0.3 中清空该设置、保存并重启以恢复默认鉴权；统一配置将省略此空字段，同时确认初始化 JSON 也不包含该字段。保留最新库与配置后，再切换旧镜像。两版数据库兼容不表示新配置字段可直接交给旧版解析。

### 从 v1.0.1 升级到 v1.0.2

本节说明从 v1.0.1 升级到 v1.0.2，改动见[更新记录](../CHANGELOG.md#102)。新镜像与旧库的兼容性不同，切换前先备份；GHCR 镜像需在对应标签的 Release image 工作流成功后核对并使用，保留 v1.0.1 标签和升级前备份。

从 v1.0.1 直接升级至 v1.0.3 也会经历下述 schema 15 → 16 变化，并同时适用上方的鉴权配置说明。从 v1.0.1 直接升级至 v1.0.4 还会继续迁移到 schema 17，按 v1.0.4 的备份和回退要求操作。

| 操作 | 数据与保护状态 |
| --- | --- |
| 新镜像沿用原数据目录启动 | 首次打开时在事务内从 schema 15 升到 16；卡 ID、名称、号码、按卡通知偏好、历史和已有迁移确认保留 |
| 仅生成或检查旧备份 | `backup` 和 `inspect` 不迁移原数据库；旧 ZIP 仍为 schema 15 |
| 将旧 ZIP 用新版工具恢复到新目录 | 恢复副本升级到 schema 16；重新进入外发保护，旧待通知任务暂停 |
| 将新版数据交给 v1.0.1 | 旧程序拒绝打开 schema 16；回退需使用兼容的升级前备份或停服数据副本 |

此次同机升级通常选择第一行：准备新镜像、备份、短暂停服并切换镜像，保留原数据卷和所有私有配置，无需先导出再恢复数据库。确认新镜像准备好后再切换，避免长时间停服。需要精确回退点时，在旧实例停止后用维护工具再保存最终 ZIP；不要只复制运行中的 `sim.db` 而遗漏 WAL。

升级本身不创建或重放历史通知，已有待推送/重试任务继续按原规则运行；已成功任务保持成功。此前外发保护已解除的实例不会因为 schema 升级重新进入保护；此前仍受保护的实例继续受保护。正常启动既有规则仍适用：未结束来电标为结果未知，已尝试但结果未定的外发不自动重发。

新页面能按固定卡 ID 显示历史记录缺失的名称，但不回填原始快照；旧分片的总数仍可能未知，不会因升级自动补齐、合并或重新通知。升级验收先核对历史、当前双卡状态、配置与版本，再等待自然到达的短信观察新诊断，无需重复全套联调。

回退前保留升级后的最新库和配置。旧备份仅包含备份时的数据，之后的新短信、通知或外发结果不会自动合并回旧版；涉及收费历史时先核对完整记录，再考虑恢复后的外发确认。

### 1. 升级前保留可回退副本

在网页保存当前数据库备份；另行私密备份 `.env`、初始化 JSON、私有 Compose 文件和数据目录内 `system.private.json`。记录当前镜像 ID、版本、数据卷、数据子目录、端口及卡状态。备份后如仍有新增记录，切换前再生成最终备份；保留旧镜像与数据卷，供验收与回退使用。若需要保留切换前的精确运行副本，可在新镜像准备完成后短暂停服、备份整个数据目录（包含数据库、WAL 与统一配置），再启动新版。

重要实例建议先在隔离数据副本上完成恢复演练。

### 2. 先准备新镜像，再改版本覆盖文件

按上节从标签构建或拉取固定镜像，确认成功后，在现有项目根目录创建 `deploy/release.private.yaml`。已有该文件时核对当前内容后编辑：

```yaml
services:
  sim:
    image: sim-harbor:1.1.3
```

使用 GHCR 时将 image 换成已验证的完整镜像引用。这个文件集中设置发布镜像，端口、配置、数据挂载与运行策略沿用原文件。旧私有文件若固定了 `sim:旧版本`，本文件必须放在最后以使新镜像生效。

### 3. 核对配置并切换

```sh
docker compose --env-file .env -p sim \
  -f compose.yaml -f deploy/site.private.yaml -f deploy/release.private.yaml \
  config --quiet

docker compose --env-file .env -p sim \
  -f compose.yaml -f deploy/site.private.yaml -f deploy/release.private.yaml \
  up -d --no-build --pull never --wait --wait-timeout 60

docker compose --env-file .env -p sim \
  -f compose.yaml -f deploy/site.private.yaml -f deploy/release.private.yaml ps
```

应用重建期间连接会短暂中断，板子随后重连，原配置和数据卷继续使用。若 `up` 失败，保留现场数据与日志，按[故障排查](troubleshooting.md)定位后继续。

以后通过终端重启、停服或升级时，继续携带相同三个文件。网页内保存配置后，也可直接使用“确认重启应用”。`config --quiet` 防止输出展开后的密钥。

### 4. 升级验收

- 容器健康、镜像版本/架构正确；网页或已认证 API 的 `version` 为 `1.1.3`。
- 数据目录、卷、HTTP/TCP 端口及私有配置未意外变化；历史、卡名称、备注和推送开关保持。
- 板子重连后查询新鲜状态，确认当前会话、两卡身份和注册情况。
- 自然到达的短信能入库，按卡通知和点击链接正常；如需 Bark 连接测试，由操作者确认执行。
- 已有恢复保护在升级后继续保留。需要外发时，按“数据维护”的迁移确认流程核对，再按需启用外发并逐条验证目标、费用和结果。
- 结果待定时查询原操作，核对后保存本版新备份，并安排稳定运行观察。

## 回退

先保存当前最新数据与配置，核对旧镜像与当前数据的兼容性，再选择回退方式：

- **数据兼容**：将版本覆盖文件改为保留的旧镜像，沿用相同项目名与挂载重建，随后核对。
- **需要旧版数据副本**：停止应用、保留当前目录，将兼容备份恢复到全新目录并协调运行配置后，再用旧镜像启动。两份数据都保留供核对。

恢复旧备份时，结合保留的新库核对备份后的新增记录；恢复实例重新进入外发保护，按迁移确认流程处理。若需完整保留当前业务状态，也可选择保留现场并修复当前版本。

回退操作参照[数据维护](data-maintenance.md)。新版本稳定、备份可用且回退窗口结束后，可清理旧镜像，同时保留当前使用的数据卷。

## 更新后的清理

先核对空间和镜像引用。没有可回收资源时无需清理：

```sh
docker system df
```

旧镜像只按明确的仓库与版本标签清理；先确认没有任何容器（包括已停止容器）引用它，并且回退窗口已结束。不使用强制删除。数据卷、配置、日志、录音、备份和其他项目资源保留。构建缓存可能由多个项目共用，不作为单项目升级后的默认清理项。

原镜像与升级前备份保留到回退窗口结束，再按具体名称清理。Git 源码目录可用 `git gc` 做常规整理；私有配置、备份与运行卷分别管理。

镜像发布实现参考 [GitHub 官方容器发布说明](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images)与 [Docker 多架构构建说明](https://docs.docker.com/build/ci/github-actions/multi-platform/)。

## 公网录音配置的兼容性

公网录音入口从 v1.1.1-rc.4 起支持，不包含在 rc.3 及更早镜像中。容量提醒去重进度单独保存在数据目录的 `voicemail-capacity.private.json`；v1.1.2 起另在数据库记录可查询的容量任务历史，随 ZIP 保存。rc.4 使用 schema 19，rc.5 与正式版 v1.1.1 使用 schema 20，v1.1.2 / v1.1.3 使用 schema 21；旧配置缺少新字段时沿用局域网 HTTP，保留地址、令牌、卡槽、设备白名单和既有开关，无需为升级修改配置或板子。

主动选择公网模式后，配置可能包含 `voicemail_upload_mode`、`voicemail_proxy_cidrs`、`voicemail_max_storage_mib`，rc.3 及更早版本采用严格字段校验，不能直接读取这些字段。回退前保留最新配置与录音目录，在新版先关闭应用录音接收并重启，按需另行停用板子；准备独立的旧版兼容私有配置，移除上述三个字段，并清空公网 `voicemail_amr_url`（旧版只接受局域网 HTTP）。不要把公网模式直接切回局域网但保留 HTTPS 地址后保存。配置兼容不能替代数据库兼容：从 rc.5 或 v1.1.1 及后续版本回退到 schema 19 的旧程序，还必须使用兼容旧版的升级前数据库；schema 19 也不能交给已发布的 v1.0.4。核对后再按原项目和 Compose 文件操作，不自动回退或删除录音。
