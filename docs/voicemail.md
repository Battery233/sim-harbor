# 留言

留言默认关闭。已发布 v1.1.0 至 v1.1.1-rc.3 仅支持局域网 HTTP；公网 HTTPS 接收从 v1.1.1-rc.4 起支持，具体固件的 TLS 兼容性与上传稳定性需在部署环境核对。在“录音配置”页依次准备应用接收、核对板子设置，两步分别确认：

| 设置位置 | 控制什么 | 何时生效 |
| --- | --- | --- |
| 录音配置 → 应用接收与提示语 | 接通后播放提示语，接收和保存录音 | 保存并重启应用后 |
| 录音配置 → 板子接听与上传 | 板子是否自动接听、录音，以及向哪里上传 | 确认执行后，以板子返回的结果为准；显示待确认时不能认定已生效 |

上传地址只在第一步编辑。第二步展示板子通过 TCP `askamrurl` 返回的地址和应用当前接收地址，隐藏路径令牌及查询参数，并按完整地址核对是否一致；“未设置”表示读回为空，不表示 TCP 无法查询。接听模式或板子预设提示语不能通过 TCP 读回时，分别显示未确认，不影响上传地址查询。开启会同步应用当前已生效的地址，停用会清空整块板子共用的上传地址。

应用设置未保存、尚待重启或保存结果不确定时，不允许启用板子。录音配置和系统配置分别保存各自的设置；发生版本冲突时，重新读取后再保存。重启会使所有已保存的应用配置生效，不只本页。

已有 v1.1.0 / v1.1.1-rc.1 配置可直接沿用；页面移动不会生成新地址或令牌，也不会自动向板子下发配置。生成模板只在地址为空时提供，仍需操作者补全相应的局域网主机地址或 HTTPS 上传域名。

首次开启时，先在录音配置填写应用选项，保存并重启应用，再在同页读取并确认板子设置。录音上传后，应用只在能唯一对应来电时关联，并发送 Bark「有留言」。

关闭应用留言服务并重启后，应用不再播放提示语或接收新录音，已有录音保留。板子仍可能接听、录音和尝试上传，应用会拒绝新的上传。要彻底停用，还需在“录音配置”的第二步停止自动接听，并清除板子提示语和上传地址。

上传方式独立于应用的本地或云端部署环境。旧配置不含方式字段时，保持局域网直连；只有主动选择公网入口才使用 HTTPS 与指定代理校验。管理地址 `public_url` 用于通知详情，上传地址用于板子提交录音，两者分别配置。

云端录音与包含录音文件的备份进度见[开发规划](roadmap.md)。

开启留言后，已接通的来电等录音关联后提醒；接听前已挂断且结束报告明确未接的来电仍提醒。自动接听可能产生通话费用，录音时长以板子固件默认为准。

## 行为

| 状态 | 来电上报 | 板子 | Bark |
| --- | --- | --- | --- |
| 默认关闭 | 记录振铃、接通和结束 | 不下发任何来电控制命令 | 未接仍按原规则提醒 |
| 已开启的卡槽 | 记录上报。602 且 `telConnectedTs` 大于 0 时，Harbor 发送一次 `telstarttts` | 自动接听和录音来自事先下发的来电方式与上传地址。提示音由这一次 TCP 播放 | 明确未接时发未接提醒；已接通并结束后等待 3 分钟，录音仍未关联时发缺失提醒，之后录音到达再发迟到提醒。只有振铃开始而没有结束报告时，不生成留言卡槽的超时兜底提醒 |
| 未选中的卡槽 | 与默认关闭相同 | 保持读回时的原值，接通后不发送 `telstarttts` | 未接规则不变 |

v1.1.1 增加录音等待提醒：从应用首次收到足以确认“已接通并结束”的上报时计时 3 分钟，使用服务端接收时间，重报不重置。正常到达的录音仍发送「有留言」；超时生成「来电已接通，录音未收到」，正文包含来电者（匿名时明确标注）、来电时间及等待说明。这里只表示未收到可关联的录音，不能断言板子没有录音。

缺失提醒已经尝试发送后，录音迟到并关联成功，会再生成「迟到的录音已收到」，说明此前缺失的录音现已保存，并跳转同一通来电。每通来电最多各有一条缺失任务和迟到任务，重报、重启不会新建同阶段任务。若缺失提醒尚未尝试发送，录音先到，就合并成普通「有留言」；若缺失推送失败或响应未知后录音到达，停止重试过时的“未收到”，改发迟到提醒。Bark 响应丢失时，推送重试仍可能重复送达，不能承诺接收端严格一次。

等待仅对本版本新确认结束且启用留言的卡槽生效，不为升级前的历史来电补建；普通重启保留截止时间。卡片关闭通知或关闭对应留言卡槽会停止未完成的等待提醒；备份恢复清除旧等待并暂停旧任务，不补发历史提醒。只有接通但没有足够结束信息时，继续展示待核对，不按通话已结束计算 3 分钟。

接通后的命令是 `telstarttts`：`p1` 为卡槽数字，`p2` 为应用接收设置里的提示语，`p3` 为 `1`（只播放一轮；缺省 0 会一直循环），`p5` 为 `0`（播完不挂断，线路留给来电者留言）。不发送 `p4`。同一通来电只发一次，键是卡槽、`telStartTs` 和 `telConnectedTs`。未接通的 601，以及 602 但接通时间为 0，或缺少开始时间，都不发送。命令若要等待其他板子操作，发送前会再核对原来电仍未结束，并且仍是该卡槽上开始时间最新的未结束来电。原来电已结束、被更晚的未结束来电代替、身份对不上或连接已换，就放弃这条提示音，不会顺延到下一通，也不会自动重试。发得太早时板子回 `code=200`「No call in progress」。

接受结果是 `type=401`、`subType=26`、`code=0`。不把 `type=402` 当成这条命令的成功，也不等待 687 / 689。失败不自动重发。`p5=1` 不用作留言结束条件。应用仍不发送 `telanswer`、`telstartrecord`、`teldial` 或 `telhangup`。

来电方式为模式 2 时，板子从接听就开始录音。提示音下行和来电者的留言可能进同一段 AMR。

## 配置核对与运行记录

板子配置的接听方式、预设提示语和上传地址，与应用接通后临时下发的提示语分别展示。当前固件不能 TCP 读回接听方式时，页面显示「需在板子后台核对」，不表示功能失败，也不要求重复发送设置短信来消除提示。

「最近运行记录」按卡槽展示最近接通上报、是否收到结束上报，以及该通来电的关联录音是否实际可读；只恢复索引但文件不在时明确提示不可读取。每 30 秒或手动刷新，仅查询应用数据，不发送板子命令。这些记录不能替代板子持久配置核对，也不能证明来电者听到了语音。

## 网页播放

来电记录里的「播放留言」使用和管理下载相同的凭据，请求 `GET /api/calls/{id}/voicemail`。服务端仍返回原始 AMR，不在镜像里转码。页面在点击后加载 opencore-amr 的 WASM 解码器，得到 PCM，再交给 Web Audio 播放。同一时间只播放一条，离开来电页即停止。「下载 AMR」仍保存原始文件。

折叠的来电行也会显示 `📼 未播放` / `📼 已播放`。同号码汇总统计该组所有录音，不只看最新一通；组内仍有未播放的录音时显示“未播放”。成功开始播放后才更新标记，下载或解码失败不改变标记。播放状态仅保存在当前浏览器，换浏览器或清除网站数据会重置，不表示其他设备或 Bark 已读。匿名来电、未提供号码或卡身份未确认时仍逐次展示，避免将不同来电者合并。

播放和下载按钮右侧提供小垃圾桶。确认后永久删除这一段录音，保留通话记录、已发送通知及录音去重凭据，来电详情在原推送结果旁标注“录音已删除”；尚未发送的留言通知取消，同一录音重报不会恢复文件或新增通知。删除对已关联和未关联录音都适用，应用接收关闭时也可操作。若文件本来缺失，可删除对应录音索引的展示。已开始的下载可能继续完成，其他人保存的副本不受影响。中断后不自动重发删除请求；先刷新列表核对。文件清理异常会记诊断，启动时只重试已确认删除的文件，不清理其他文件。删除标记保留在既有录音索引字段中；录音等待与迟到通知使用 schema 20，恢复较早数据库和录音副本会恢复当时状态。

录音配置的板子设置区域显示**应用录音存储**：`voicemail/` 中的文件数、实际文件长度合计及公网模式上限，包含未关联及中断遗留文件；它不是板子文件系统统计。每 30 秒及删除后刷新，也可手动刷新。删除索引仍保留去重凭据，现有最多 10000 条录音索引保护不因删除文件而重置。

板子上传的是 AMR-NB（文件头 `#!AMR`），按 8000 Hz 单声道播放。现代 Chromium 和 Firefox 可以播放。`<audio>` 不能直接播放 AMR。页面的内容安全策略允许编译这段 WASM（`wasm-unsafe-eval`），不放宽脚本 `eval`。解码失败时下载仍然可用。

Safari 不作为这条能力的验收目标。没有 Web Audio 的浏览器会提示无法播放，下载不受影响。

## 未关联录音

“录音配置”页底部的“未关联录音”展示应用已保存、尚未对应到某次来电的录音。列表按保存顺序从新到旧排列，每页最多 50 条，可刷新和加载更早记录；展示上传卡槽、来电号码、通话开始时间、上传保存时间、文件名和大小。上传未提供的信息保留为“未提供”，不按当前 SIM 或接收时间补猜。

文件可读时，可直接播放或下载原始 AMR；权限与管理页面一致，不能仅凭上传令牌读取。应用接收开关关闭或当前为云端部署，也可查看该实例原有数据中的未关联录音，不因此自动开启新的上传接收。文件缺失、不可读或大小与索引不同会单独提示，并禁用播放和下载；数据库 ZIP 不含 AMR，恢复索引后仍需单独放回 `voicemail/`。

查看列表不修改关联、不发送通知，也不向板子发命令。自动关联规则保持原样：后续来电上报、重复上传或应用重启时重新尝试；关联成功后刷新列表，该录音不再出现在这里，改从对应来电查看。列表尚未刷新时点击已关联录音，会提示刷新。当前不提供手动关联。播放、下载按钮右侧的小垃圾桶可在确认后逐条删除录音。

## 开启

能访问板子的 `/mgr` 时，也可手动配置来电应答和同一个录音上传地址，不必再执行重复的设置短信。手动设置不等于应用已经核实；无法通过 TCP 查询的项目仍需在板子后台确认。

1. 确认板子来电策略目前是“不接听”，录音地址为空。需要留言时再继续。
2. 在“录音配置”的第一步填写卡槽、提示语、上传方式和上传地址。局域网模板需替换 `192.168.31.x` 并核对发布端口；公网方式需先按下节准备 HTTPS 代理入口。
3. 勾选留言确认和保存确认，保存后重启应用。重启前运行中的进程仍按旧配置工作。
4. 在同页第二步读取板子设置。读取只走 TCP，不发短信。
5. 确认启用。上传地址用 TCP `setamrurl`。来电方式先试 TCP `slotcim` 模式 2；X32v158 拒绝时，改为从所选卡槽向该卡自己的号码发送 `*#slotNcim#`。启用不再写入 `slottts` 提示音预设，因此短信确认也不再为提示音发指令。其他卡槽不发指令。提示音留在 Harbor，等这张卡接通后再发 `telstarttts`。

局域网模式的上传地址必须是板子能访问的 HTTP，例如 `http://192.168.31.10:18880/api/voicemail/amr/<32位以上十六进制令牌>?slot={{slot}}&start={{telStartTs}}&phone={{phNum|$urlEncode()}}`。要求显式端口、IPv4 私网或本机地址，以及上述路径。该模式不接受公网域名、`nip.io` 或无端口地址。令牌由浏览器随机生成，不是管理凭据。

板子上传不带管理 Bearer。局域网接口在留言已启用时，同时检查路径令牌和来源 IP 是否落在设备白名单。白名单关闭时拒绝上传；页面显示当前生效的白名单与来源规则，新的启用操作会被阻止，停用和只读查询不受影响。不要把局域网接收策略直接放到公开代理后面；经代理上传应主动选择公网模式。

## 本地部署

现有 Compose 默认把网页发布在 `127.0.0.1`。板子访问不到这个地址。留言上传要在宿主把容器 `8080` 发布到局域网 IP 和端口，例如 `192.168.31.10:18880`。容器内部仍监听 `8080`。不要为了留言把默认绑定改成 `0.0.0.0`。云端服务器上的管理入口不能充当这块上传地址。

用覆盖文件增加局域网发布，并保留原来的项目名和数据卷。地址按这台主机的局域网网卡替换：

```yaml
services:
  sim:
    ports:
      - "192.168.31.10:18880:8080"
      - "192.168.31.10:39090:9000"
```

`setamrurl` 使用宿主局域网 IP 和发布端口，不是容器端口 `8080`，也不是 `127.0.0.1`。设备白名单写入板子自己的来源地址，例如 `192.168.31.20/32`，这样上传的来源就是板子。此模式要求应用看到的 HTTP 对端就是白名单中的板子；不读取任何转发来源头。经反向代理上传请使用公网模式及独立代理来源规则。

升级前先备份数据库和 `system.private.json`，并单独复制数据目录里的 `voicemail/`。SQLite ZIP 含留言索引，不含 AMR 文件。只恢复 ZIP 不会把录音文件带回来。

v1.1.0 在首次启动时将数据库升级至 schema 19，留言保持关闭也会升级。schema 18 增加留言索引，schema 19 增加不含密码的控制短信账本。已发布的 v1.0.4 不能打开 schema 18 或 19。退回 v1.0.4 时使用升级前的备份，不要手改 `schema_version`。v1.0.4 的短信组装、持久去重和默认来电记录行为保持不变。

## 数据库兼容性（v1.1.1）

录音等待及迟到通知将数据库升级到 schema 20，增加持久等待截止时间及通知阶段；旧配置无需修改。备份 ZIP 仍使用格式 1，包含这些状态，不包含 AMR。schema 19 及更早的兼容备份可由新版恢复并迁移；旧版 v1.1.0 至 v1.1.1-rc.4 不能直接打开 schema 20。回退使用升级前数据库，不手改版本号。

## 公网录音接收

本节适用于 v1.1.1-rc.4 及后续支持公网录音的版本。板子使用完整的 `https://上传域名/api/voicemail/amr/<32至64位随机十六进制令牌>?slot={{slot}}&start={{telStartTs}}&phone={{phNum|$urlEncode()}}`，不要填写应用的内部监听地址。厂商文档支持 HTTPS，但具体固件的证书兼容、上传事件与最终落盘仍需现场验证，见[厂家资料入口](reference/board/README.md)。

1. 准备独立 HTTPS 上传域名，通过已有或单独的 Tunnel 转发到本机 HTTP，例如 `http://127.0.0.1:18880`。只路由完整的 `/api/voicemail/amr/<令牌>` 路径，其他路径拒绝；示例见[录音 Tunnel 路由](../deploy/cloudflared-upload.example.yml)。不为此放开服务器的 HTTP 公网端口。
2. 上传域名不要求 Access 邮箱登录、验证码或交互式挑战，否则板子无法完成 POST。管理域名仍保留 Access 与应用管理员 Token。外部入口强制 HTTPS，避免重定向上传；保留请求路径、查询参数和请求体，不记录完整地址、令牌、来电号码或录音正文。
3. 在“录音配置”选择“公网入口（HTTPS）”，填写该完整上传地址。地址中的随机令牌就是上传凭据，无需单独设置；生成模板只在空地址时提供，切换方式不会改写旧地址或令牌。
4. 展开“公网接收保护”，核对应用实际看到的代理 IP。默认只允许 `127.0.0.1/32`、`::1/128`；显式填写后仅信任填写的地址。只允许单个私网或回环 IP（`/32` 或 `/128`），不要填板子公网 IP、Cloudflare 公网网段或整个 Docker 子网。宿主 cloudflared 转发到 Docker 发布端口时，应用可能看到网桥网关 IP，需根据实际网络填写该单 IP，并保持宿主 HTTP 仅绑定回环。此规则与设备 TCP 白名单独立，不修改设备接入规则。
5. 核对录音目录容量上限，默认 512 MiB，允许 16～65536 MiB。保存并确认重启应用，再读取板子设置，预览并确认启用；不会因保存应用设置自动发短信。既有白名单、板子目标、上传路径及令牌不会自动改变。

接收时先确认来自指定代理，再对地址中的路径令牌作恒定时间比较。不信任 `X-Forwarded-For`、`CF-Connecting-IP` 或 `X-Forwarded-Proto`；不根据请求声称的客户端 IP 放行。因此指定代理必须是自己控制的入口，不能把一个会让陌生人伪装成本机来源的代理加入信任。HTTPS 由该代理入口保证，应用不会通过内部 HTTP 请求判断板子到入口是否加密。

上传凭据只允许提交录音，不允许读取管理 API、播放或下载。页面通过 TCP 读回板子地址后仍比较完整地址；接收上传时只核对路径中的令牌，不要求内部 HTTP 的主机名和协议等于公网 HTTPS。查询参数用于关联来电，不能因转发而丢失。Cloudflare Tunnel 原样转发完整路径，额外的 URL Rewrite、Worker 或中间反代配置仍需自行核对，见[官方路径转发说明](https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/configuration-file/#how-traffic-is-matched)。

公网接收限制：单个 AMR 最多 2 MiB，请求体最多另加 64 KiB 包装；全入口最多同时处理 2 个请求，令牌桶允许短时 10 次请求、持续每秒补充 1 次额度（每分钟 60 次），错误令牌也消耗额度，超限返回 `429`。预算在应用重启后重置，不能替代 Cloudflare 边缘的流量控制，也不保证攻击期间正常上传可用。容量按录音目录实际文件（包含中断遗留文件）计数，最多 10000 条索引/目录项；达到限制返回 `507`，不删旧文件，已保存的同一录音重报仍可去重成功。它不预留磁盘空间，磁盘不足仍可能导致保存失败。

容量提醒：开启公网接收且已配置 Bark 时，后台每 30 秒核对录音目录大小。达到上限一半时提醒，此后每增加 32 MiB 再提醒；默认 512 MiB 对应 256、288、320 MiB 等提醒点。一次跨过多个提醒点只发送一条当前状态，避免补发多条。提醒包含已用、上限和剩余容量，不含号码、文件名、令牌或录音内容。它独立于单卡静音及板子持续异常提醒开关，恢复保护未解除时不推送；未配置 Bark、接收关闭或局域网模式不推送。

已提醒进度保存在数据目录的 `voicemail-capacity.private.json`，不会因应用重启重复同一提醒；失败按 30 秒起、最长 1 小时退避重试。响应丢失或进程在 Bark 接受后退出，仍可能重试同一条，不承诺接收端严格只收到一次。占用降回一半以下后重新计数；修改容量上限时按新阈值计算。该文件不包含在数据库 ZIP 中，需随私有数据目录保留；丢失文件后会按当前容量重新提醒。状态文件损坏或无法保存时，停止该次提醒并记录诊断，不影响录音接收，不自动清空提醒状态。此处只统计 `voicemail/` 中文件长度之和（含已关联、未关联和中断遗留文件），不统计数据库、日志、备份或整块磁盘；它不是磁盘剩余空间监控。

沿用原来的 `voicemail/` 路径、关联与去重规则，HTTPS 和上传令牌都不是磁盘文件加密。数据库 ZIP 仍不含 AMR；变更配置后的旧版回退要求见[配置兼容性](releases.md#公网录音配置的兼容性)。

## 关闭并恢复

页面上的“已保存”表示下次重启将使用的设置，“当前生效”表示应用现在使用的设置。这两项都不代表板子已经停止接听。

1. 在“录音配置”取消应用接收并保存。这时只是已保存配置改为关。若还没重启，运行配置可能仍是开。页面会写明关闭应用开关不会自动停止板子接听。
2. 重启管理应用后，运行配置才关闭留言服务。新的来电按默认未接提醒和超时兜底规则处理，应用也不再接收录音。板子自动接听不会因此撤销。
3. 在同页第二步重新读取，选择“停用：停止自动接听，清除板子预设提示语和上传地址”，核对预览后确认执行。预览列出目标卡槽、提示语和上传地址的修改，以及预计短信条数。需要发送设置短信时，单独确认停用和费用。短信已提交或被板子接受不等于设置已生效；显示“尚未确认停止自动接听”时，先重新读取，不要重复操作。

运行配置未选卡槽时，TCP 恢复会按读回的来电方式和提示音确定需要恢复的卡槽，并清空上传地址；即使只剩上传地址，也可以单独清空。短信通道无法完整读回来电参数，仍须在运行配置中指定卡槽。应用留言服务关闭不妨碍恢复板子；预览不可执行时，确认按钮不可用。

## 板子命令

厂家 TCP 目录里，录音地址是 `askamrurl`（子类型 56）和 `setamrurl`（子类型 55）。来电方式 `slotcim` 和提示音预设 `slottts` 只有短信指令，没有对应的 TCP 页面。接通后的提示音使用 TCP `telstarttts`，接受回执是 `type=401`、`subType=26`。X32v158 对 TCP `slotcim` 回 401 时，读取仍返回 `askamrurl` 的结果，来电方式标为 TCP 未返回，并且不因此中断查询，也不再接着查询 `slottts`。

确认启用时只写上传地址和来电方式。TCP `slotcim` 被拒绝时，应用从所选卡槽发出短信，收件号码填这张卡自己的号码：

- 来电方式：`*#slot2cim#用户密码#2`（接听并录音）或 `#0`（不接听）。不改响铃次数和最长通话。
- 启用不发送 `*#slotNtts#`。提示音里的 `#`、`@`、`&`、`~` 可以保留，因为接通后走 TCP JSON，不进短信正文。

若板子上还留着以前写入的 `slottts` 预设，接通时预设和 `telstarttts` 会各播一次。恢复会清空这个预设：TCP 能写时用 `slottts` 把文字置空；只能走短信时发送 `*#slot2tts#用户密码#`（密码后不带文字）。需要只保留 Harbor 的一轮提示音时，先恢复再启用。

用户密码在确认时输入，不写入配置、账本、发件记录或 Bark。带有指令格式的短信不进收件箱。出厂密码是 `000000`；改过则以板子为准。密码错误时板子 30 分钟内可能只回复一次。密码本身不能含 `#`、`@`、`&`、`~` 或空格。

短信指令会占用这条卡的短信，可能产生费用。读取不会发送。只对应用接收设置里选中的卡槽发，卡槽为空时不要选它。两张卡各自填写自己的本机号码，应用会分别和状态里的号码核对。

启用留言使用普通外发的限制：恢复保护未解除或外发未开启时不发送。停止自动接听要另勾确认；这时即使外发关闭或恢复保护还在，也只发送停止自动接听所需的短信，不会变成一条普通外发。

发送前把不含密码的记录写成“可能已发出”。控制短信和普通外发共用这张卡的发送间隔和每日限额。同一次确认里的下一条必要短信可以不受间隔限制，但每条仍占当日额度。账本按卡槽把还没被拒绝的控制记录连成一次操作。同一类指令重复同一目标时，如果这张卡槽之后没有新的未拒绝记录，就不再发送，结果未知或重启后也一样。中间做过另一次控制（例如恢复之后再启用）后，下一次恢复是新的操作：来电方式可以再改回不接听，清空提示音也可以再次发送，并且仍会清空上传地址。同一操作里已经记过的某一步不会让整次恢复失败，后面还没完成的步骤继续做；没有新记录时不会重发，也不会把跳过的步骤显示成已经确认。

X32v158 上，这条控制短信经常没有 type 501 回报（看不到「设置为来电」或「已经取消」）。板子仍然可能已经执行。Harbor 把缺少 501 记为已提交、待确认，不因此返回 502，也不把要下发的来电方式或提示音抄进读回结果。判定是：

- 尚未看到板子接受时，状态是已提交。
- 401 code 0 表示正在发送，402 表示命令已处理，502 / 503 是提交或送达类回执。这些只说明短信被接受，不说明来电方式已经改完。见到 402、502 或 503 后，最多再等大约一秒，以便收下已经在路上的 501。
- 若 501 真的到来，先核对来源号码、实际卡槽和可确认的 SIM 身份，并且短信时间不能早于这次发送。正文里写了“卡槽2”不够。对得上之后，正文符合本次指令才把对应参数标为已确认；正文是密码错误或格式错误则仍然失败。对不上的短信留在收件箱，不改变这次操作。早于这次发送的旧回复同样不能当成这次的结果。模式 2 的回复可能写成“N 声后自动挂断”，这是固件文案，应用只在本次下发的是模式 2 时把它当成接听并录音。
- 上传地址仍用 TCP 单独读回，和来电方式是否确认分开显示。

接通后是否自动接听，用打电话确认；提示音是否播放，看 Harbor 是否发出 `telstarttts`。再次点“读取”时，来电方式仍可能显示 TCP 未返回。这表示固件没有 TCP 查询，不表示刚才的短信失败，也不表示目标值已经生效。

只有和某次控制短信的卡槽、来源号码、可确认 SIM 身份都对得上，且短信时间不早于那次发送的回执，才不进收件箱。留言关闭、没有这笔账本，或其他号码、其他卡槽、换过的 SIM、缺少 SIM 身份或迟到的旧回复，包括正文里出现“设置为来电”，都照常保存和提醒。

录音优先按卡槽、开始时间和号码精确关联。时间差一点时，同号码的候选都保留，包括还没有卡身份的那一通。只剩一个候选且这通来电有卡身份才关联。不能先丢掉身份未知的来电，再把剩下的一条当成已经核对。号码写法可以带国家码。对不上、有多条候选、换过卡、没有卡身份或匿名来电时保持未关联，也不把“同卡槽最近一通”当成同一通。录音比来电先到、重复上传或应用重启后，用同样的规则再关联一次。文件只留一份，不重复来电通知；卡的静音和恢复后的通知保护保持原样。

## 核对

下面是可重复的产品核对，不依赖某一台机器或镜像标签。合成测试覆盖这些边界，但不能代替 v153 或其他固件的真机验收。板子外网保持阻断，上传只走局域网。

1. 留言关闭时打一通测试电话：只有来电记录和未接提醒，TCP 上没有接听、拒接、拨号或录音命令。收件箱仍保存普通短信。
2. 读取留言参数不会发送 `sendsms`，也不会改来电方式或提示音。
3. 启用前确认外发已开、恢复保护已解除，并勾选费用。号码必须是该卡当前的本机号码。启用确认里没有 `slottts` 或提示音短信。
4. 没有 501 时，页面写明短信已提交、来电方式尚未确认，并且不自动再发一次。有明确的模式回复时，才显示已确认。
5. 停止自动接听单独确认。外发关闭时这条停止短信仍可发出；启用留言则不能。
6. 向该卡槽打电话。板子自动接听后，Harbor 发送一次 `telstarttts`，提示音只播放一轮且不挂断，通话结束后 Harbor 收到 AMR。录音里可能混有这段提示音。
7. 来电记录可以播放或下载 AMR。播放走同一管理凭据，在浏览器里解码 AMR-NB；下载仍是原始文件。Bark 标题含「有留言」。同一录音重复上传不产生第二条通知。对不上的录音不挂到另一通来电上。
8. 未开启留言的另一卡槽仍只记录，不自动接听。
9. 关闭时先关掉应用开关并重启，再对板子做一次恢复。再打电话应回到只记录、不接听。
10. 备份 ZIP 后，另存 `voicemail/`。只恢复 ZIP 时索引还在，未关联录音列表会标记文件缺失，播放或下载也不能带回文件，要等录音目录放回。已保存和未关联的录音都不会自动删除；支持确认后逐条删除；不会自动删除旧录音，手动关联留待后续。
11. 页面组件和合成 AMR 解码覆盖现代 Chromium 与 Firefox。Safari 不在验收范围。这些检查不是 v153 或其他固件的真机通过记录，也不是浏览器音频的跨机验收。
12. 升级 v1.1.0 前先保存兼容旧版的备份。即使留言保持关闭，数据库也会升到 schema 19。已发布的 v1.0.4 不能打开升级后的库。退回时使用升级前备份，不要移动既有版本标签。
