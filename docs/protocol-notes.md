# 协议说明

设备通过原生 TCP 完成事件上报、状态查询和命令响应，本地与云端共用协议路径；录音文件走独立 HTTP/HTTPS 上传。X 系列 v153 固件的短信、来电与状态等基础链路已完成真机验收，扩展能力仍需按目标固件核对，协议字段与其他型号接入可参考[厂家在线文档](reference/board/README.md)。

## 帧与状态

实现处理 TCP 分段/合并、帧解析、设备标识、事务关联及超时。有效帧经过业务校验再持久化；日志使用摘要与失败类别帮助定位问题，并保护载荷和凭据隐私。

状态查询使用有效会话及新鲜度判断。卡身份以有效 ICCID 关联固定 ID，卡槽只是当前物理位置；缺失身份时明确标为未知。事件时间按配置时区解释，设备事件时间与应用接收时间分别处理。

## 短信与来电

收件解析会保留原始正文语义、长短信分片与完成状态，并去重持久化；通知只在满足完整性条件后创建。显示转义选项不改变保存的原文。

长短信额外保存总片数和匿名组引用，同一业务记录后续报告的总片数必须与已保存的非零总数一致，冲突事件回滚并保留已有分片。升级旧库不会根据正文或已有分片猜测总数；后续匹配上报可提供总数，但应用无法核对升级前未保存的总数是否曾与其不同。

默认信息级别日志记录成功解析并通过设备标识检查的长短信上报：匿名组引用、短信时间、总片数、本次分片序号、板子完整标记，以及入库事务结果；日志时间为应用实际接收/处理时间。没有组或分片信息的普通完整短信不记为长短信；缺少组号但明确报告未完整的事件仍记录诊断。成功入库后可读回记录编号和完整状态，诊断读回失败不影响业务结果。解密或结构解析失败仍记录通用错误类别，不输出原始报文。日志不含正文、号码、原始组号、设备或 SIM 身份。

匿名组引用关联同设备、同卡、同发送方、同组号的上报，不包含短信时间，便于发现时间变化。组号可能复用，同一引用不是永久唯一的短信编号，需结合短信时间、分片元数据与应用处理时间核对。运行诊断可按该摘要筛选，日志保留范围见[配置说明](configuration.md#日志保留)。

v1.0.2/v1.0.3 的业务组装键包含精确短信时间；同组但时间不同的上报会保存为不同记录。v1.0.4 起支持以下改进。

### 允许分片时间差的组装

保留原业务键的严格匹配，优先识别已存在或已删除的记录，再查找此前已接受的分片上报关联。只有未匹配上报才尝试以下规则：

1. 板子提供有效 SIM 身份、分组号、总片数及分片序号；设备、SIM、发送方、组号均相同，已保存的总片数与本次一致且大于 1。
2. 候选范围内只有一条短信，该记录未完成且已保存可核对的分片。多个候选、已完成记录或重叠序号内容不同，均不放宽匹配。
3. 整组已接受上报携带的 `smsTs` 最大值与最小值之差不超过 120 秒。比较的是短信时间，分片可以乱序或隔很久才通过网络到达；不会随着分片逐个到达而不断扩大时间窗口。
4. 按分片序号合并并去重，只有 1 至总片数的所有序号都存在才本地标记完整。完成时按原规则创建唯一通知任务，原有任务不重置；板子报告的完整标记与本地完整状态分别记录。

每次接受的分片业务键关联到同一短信记录，并随事务和完整数据库备份持久保存。后续按这些已接受键重报时，即使组装已完成、应用重启或短信已删除，仍能定位原记录，避免重复通知或恢复已删除内容。首次收到的卡槽、名称快照及短信时间保持不变，诊断显示本次实际携带的短信时间与组装后的记录编号。

缺少组号或 SIM 身份、旧记录缺少可核对的分组信息，以及未携带分片序号的完整聚合上报，继续按严格业务键处理。升级不会批量重组历史记录；已保存分组信息的旧未完成记录可在后续真实上报时继续组装。组号、身份、总片数、时间范围和互补序号仍不是全局唯一凭证：若来源在短时间复用全部条件且没有可见冲突，现有协议字段不能保证识别出不同短信，120 秒窗口只是应用的保守边界。

同一严格业务键的总数冲突或未完整记录中的分片内容冲突仍回滚本次事件；不同时间候选有冲突时保留为独立记录。入库错误沿用既有连接处理规则，关闭当前 TCP 连接，等待板子重新连接；应用不主动请求重传或查询板子历史。

来电开始、结束、接通和冲突信息分别处理，结束信息待定时以明确标注的提醒帮助核对。板子本地历史独立查询，应用长期历史通过业务库与一致备份管理。

留言的自动接听、录音和上传地址仍预先配置，上传方式按版本可选局域网 HTTP 或经受控代理的公网 HTTPS，见[留言说明](voicemail.md)。录音地址使用厂家 TCP `setamrurl` / `askamrurl`（子类型 55 / 56）。来电方式 `slotcim` 在厂家目录里是短信指令；TCP 查询若回 401，读取仍保留 `askamrurl` 的结果。确认启用后的模式写入改为受外发保护的 `sendsms`，投递 `*#slotNcim#`。启用不再下发 `slottts` 预设。发送前核对当前 SIM 和该卡自己的号码，先把不含密码的账本写成“可能已发出”，再写到网络。X32v158 经常不回 type 501。缺少 501 时结果是已提交、待确认，上传地址是否读回要单独看；不会把要下发的来电方式或提示音抄成读回值，也不会因此自动重发。501 若到达，只有来源号码、卡槽和可确认的 SIM 身份都对得上这次操作时，才用于确认或拒绝（密码、格式错误）。停止自动接听使用单独确认，外发关闭时仍可发送，但不是静默绕过。

提示音由 Harbor 在接通后参与一次：已启用卡槽出现 type 602 且 `telConnectedTs` 大于 0 时，发送一条 TCP `telstarttts`。`p1` 是卡槽数字，`p2` 是配置中的提示音，`p3` 为 1，`p5` 为 0。同一通电话只发一次。成功接受看 type 401、subType 26、code 0，不要求 type 402。应用不发送 `telanswer`、`telstartrecord`、`teldial` 或 `telhangup`，也不用 `p5=1` 结束留言。模式 2 从接听起录音，提示音下行可能和留言在同一段 AMR 中。以前留下的 `slottts` 预设要靠恢复清空，否则会与这一次播放叠在一起。

## 命令与结果

管理操作采用明确的命令集合、串行查询与事务关联。参数写入经过读取、确认和读回；连接中断后保留待核对结果，按原事务查询，避免重复写入。

短信外发的板子接受/处理、运营商提交和送达报告分别保存；401/402 不能证明送达，502 表示提交，503 需要唯一关联及所有分片成功才可判断相应报告。回执关联不明确时保留歧义，不按猜测认定成功。

## 加密兼容

支持配置 mode0/1/2。mode1 上行加密、下行明文，已用于真机验收；mode2 按实际固件核对双向加密兼容性。云端配置要求加密模式，本机测试可用 mode0。两端 Key/IV 与模式保持一致，再通过有效状态上报验证。

AES-CBC 不提供完整认证或防重放，设备编号不是密钥。详见[安全说明](../SECURITY.md)。
